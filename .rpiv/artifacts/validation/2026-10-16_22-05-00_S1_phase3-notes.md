# S1 phase 3: findings on the live NC 34.0.4 instance (bd-s1)

Probe scripts ran inside the `bd-s1` Nextcloud container against the real `Recheck` (throwaway users `p3*`, tags `p3tag-*`, groups `p3team*`; all removed afterwards). Nothing here breaks a design assumption, so the phase is not sent back to `/bd-design`.

## Recheck semantics on the real node API
- Group share of a folder: file inside it survives for the sharee, `snippetAllowed = true`.
- User share with `permissions.download = false`: survives with `snippetAllowed = false` (the `ISharedStorage::getShare()` attribute is reachable through NC's `Trashbin\Storage` wrapper).
- Share with a past `expiration` (set in `oc_share`): `getById` already returns no node, so the hit is dropped. The explicit expiry check in `Recheck::judge` is defence in depth, and it is what the unit tests cover.
- D1 confirmed live: tag on the shared mount root, and tag on the owner's `files` root (above the sharee's mount), both drop the inner file for the sharee. Removing the tag restores the hit. A duplicate `rag-excluded` tag cannot be created (`TagAlreadyExistsException` for the same name and flags, and the existing tag was non-public); the all-tags-count logic is unit-tested for the case where an admin created differing flags earlier.

## M5: who can assign which tag
`canUserAssignTag` for a non-admin user: public (visible + assignable) true; visible but not assignable false; invisible false. The tag created by `tests/canary/enqueue.php ensure-tag` is invisible and not assignable, so ordinary users can neither see nor assign it. Anyone able to create a *public* tag named `rag-excluded` would be a second tag with the same name: `ExclusionChecker` resolves every tag with that name, so it is still honoured, and the recheck fails closed when none exists. Open point for S3: if a public `rag-excluded` tag exists, users can assign it (intended: users opting a folder out), so the install docs must say which flavour the admin creates.

## M3: mount-cache staleness
- Revocation is immediate in a new process: after the sharee left the group and a user share was deleted, a fresh process dropped both hits (mount-cache rows were already removed by NC's hooks).
- The opposite direction is a transient false negative, never a leak: a user whose files filesystem has never been set up in the process that created the share does not see the new user-share file through `getById` until their next setup (observed once with brand-new users in the same process as the share creation; a fresh process found the group-shared file at once and, after the first setup, the user-shared one too). In production the search is a separate request from the share creation, so this window is the time to the sharee's first request.
- Consequence for U4: the canary must run each phase (share, search, revoke, search) as separate `occ`/php invocations, not in one PHP process.

## M7: multi-node download semantics
Not verifiable on the single-node bd-s1 stack. What the code relies on: the download attribute is read from the share object loaded per request through `getById` and `ISharedStorage`, and nothing in `Recheck` caches it. NC's own share and mount caches follow the configured distributed cache. Left open for S3/S5 with a ticket note; it does not block S1.
