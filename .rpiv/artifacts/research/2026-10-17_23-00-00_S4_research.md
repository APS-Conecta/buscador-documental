# S4 research: embedding profiles and hybrid search

Three read-only agents (Ollama, Postgres/pgvector, codebase) produced the findings. Repo facts marked (verified) were re-checked by me against the files; everything else is the agent's claim with its source. UNVERIFIED means no official page or runtime confirmed it.

## 1. Ollama as the embedder (sources: docs.ollama.com, github.com/ollama/ollama, ollama.com/library, Hugging Face cards)
- Endpoint `POST /api/embed` (`model`, `input` string or array, `truncate` default true, `dimensions`, `keep_alive` default 5 m, `options.num_ctx`). Returns L2-normalised vectors in `embeddings` (nested). The legacy `/api/embeddings` is superseded and does not normalise. https://docs.ollama.com/api/embed
- Overflow: with `truncate:true` the tail is cut silently; no response field says so. Send `truncate:false` and set `num_ctx` explicitly. Behaviour changed across versions (issue 14186, status UNVERIFIED).
- A model that is not pulled gives a 404 "not found, try pulling it first" (user reports, not official docs). No auto-pull.
- Candidates (dimension, context, prefixes from the HF cards; Ollama quantisation UNVERIFIED except nomic fp16):

| Model | Dim | Context | Prefixes | Licence |
|---|---|---|---|---|
| `bge-m3` (567m) | 1024 | 8192 | none | MIT |
| `qwen3-embedding:0.6b` | up to 1024 | 32K | query instruction template, none for documents | Apache-2.0 |
| `nomic-embed-text-v2-moe` | 768 (MRL to 256) | 512 | `search_query: `, `search_document: ` | Apache-2.0 |
| `embeddinggemma` (300m) | 768 | 2K | task prompts | Gemma terms (not OSI) |
| `snowflake-arctic-embed2` | UNVERIFIED | 8K | UNVERIFIED | Apache-2.0 |
| `paraphrase-multilingual` | 768 | 512 | none | UNVERIFIED |
| multilingual-e5 (the S0 model family) | 1024 large | n/a | `query: `/`passage: ` | **not in the Ollama library** (issue 4276) |

  Consequence: the S0 measurements used multilingual-e5-small (384-d), which Ollama does not serve. Every S0 vector number (index size, recall, latency) must be re-measured with the Ollama model chosen. bge-m3 (1024-d) is about 2.7x the storage per vector of 384-d.
- CPU throughput: no official figure (UNVERIFIED). Batch arrays matter (GPU example: 200 inputs 1.4 s batched vs 30 s singly); a client report of timeouts at 100 inputs per request recovered at 16. Default `OLLAMA_NUM_PARALLEL` 1; `OLLAMA_MAX_QUEUE` 512 then 503; first request after `keep_alive` expiry pays the load time.
- Pinning: `GET /api/tags` returns `digest`, `size`, `details.quantization_level`; `/api/show` returns `model_info` and context length. Tags such as `latest` can move, so pin an explicit tag and store digest at profile save; a changed digest should flag the generation as stale. Pulling by digest: UNVERIFIED.
- Security: binds 127.0.0.1:11434 by default, no authentication, pull/delete/create endpoints share the port. A non-loopback endpoint needs a TLS + auth reverse proxy that allows only `/api/embed`, `/api/tags`, `/api/show` (agent recommendation).

## 2. What the repo already has and lacks (verified unless noted)
- `Retrieve::run($uid,$query,$limit)` is keyword-only with OFFSET refill rounds; no mode, filters, sort or cursor; no controller, route or unified-search provider exists (`app/appinfo/routes.php` has only worker routes).
- Worker: lane `'text'` only. `claim_job` is lane-generic but its give-up step writes `file_state.text_state='skipped'` for any lane and the global lease cap counts all lanes (`002_functions.sql`, copy in `004_s3.sql`). The worker role can only EXECUTE `claim_job, heartbeat, write_result, fail_job, schema_version`; a vec lane needs new SECURITY DEFINER functions (fetch a claimed file's chunk texts, write vectors compare-and-set) and a `WorkerPrivilegeTest` update.
- `file_state.vec_state` exists (default 'pending', no CHECK) and is never read or written (verified by grep).
- **Orphan risk (verified):** `write_result` deletes and reinserts `chunk` rows (`002_functions.sql:121`) and does not touch `chunk_vec_*`; chunk ids change on every text re-index. S4 must invalidate or delete vectors in the same transaction and re-enqueue the vec lane. `erase_files` already loops over `chunk_vec_<n>` plain tables with a `file_id` column (`004_s3.sql`), so generation tables must be plain, not partitioned, and carry `file_id`.
- `ts_config_ver` exists in `schema_meta` but nothing in code reads it (verified grep): the "any change forces a reindex" rule is not enforced anywhere yet.
- pgvector: image `pgvector/pgvector:0.8.7-pg18` is pinned; `CREATE EXTENSION vector` is done in the stack init `db/init/00-roles.sql`, but the app migration preflight (`000_preflight.sql`) checks only `unaccent`. No `embedding_profile`, `chunk_vec_<gen>`, `profiles.yaml` or vec-lane code exists. Schema 3 means `005_s4.sql`, `Version000003`, `SUPPORTED_SCHEMA = 3` in the worker, and updated schema-version asserts in `MigrationTest`/`S3SchemaTest`.
- Where the embedder may run: not in the `parser` container (no network, untrusted bytes, no secrets). The `worker` container (DB role, HMAC secret) is the natural place for ingest embedding, needing an egress rule to the Ollama host only; today it has none. Query embedding is called from PHP, so the Nextcloud container must reach the endpoint.
- Nextcloud HTTP (verified in the 34.0.4 image layer by the agent): `IClientService` blocks local/private hosts unless system config `allow_local_remote_servers` is true or the per-request option `['nextcloud'=>['allow_local_address'=>true]]` is passed (`lib/private/Http/Client/Client.php:158-164`). Docker hostnames count as local. The per-request option plus an admin-only URL setting is narrower than the global flag. Runtime behaviour UNVERIFIED (stack not up).
- A running Ollama exists on this VPS in another stack (an open-webui project). It is not ours: do not touch it; tests use a stub embedder, and any real-model measurement needs a decision on where Ollama runs.
- No org code to reuse for Ollama. Reusable patterns: IntraVox `OutboundUrlValidator` (SSRF guard) and `AdminSettings` (delegated settings).

## 3. Postgres / pgvector facts and S0 results (sources: pgvector README/CHANGELOG, PG docs, `02-performance.md`, `results-s0`)
- `halfvec` HNSW is indexable to 4 000 dims (384 and 1024 fit). `hnsw.iterative_scan` has `strict_order` and `relaxed_order`; `max_scan_tuples` default 20 000; the README's `relaxed_order` pattern needs a MATERIALIZED CTE and `ORDER BY d + 0` on PG17+. Filters apply after the index scan.
- S0 (PG17, 3M synthetic clustered, 384-d): HNSW 3.5 GB, build 652 s at `maintenance_work_mem` 8 GB (needs matching `/dev/shm`), narrow-user filtered recall about 0.81 on the ANN path at `ef_search` 200, 1.0 on the exact path. The shipped `ef_search` 200 differs from the 100 used in the hybrid latency bench (`m7_hybrid.py:61`).
- **Doc conflict (verified):** the exact-scan switch is "~1 000 readable files" in `01-architecture.md:61` but "~2 000" in `02-performance.md:82` and ADR-0001. Design must pick one, defined on accessible chunks.
- RRF reference SQL: `spikes/s0-harness/bench/m7_hybrid.py:17-39` (two MATERIALIZED legs, `row_number`, `sum(1/(60+rank))`). Gaps: legs capped at 50 rows (too shallow for a 1 000-document cap and page 100; the bench itself says page-100 cost is understated); grouping by file is done in Python; no OR relaxation; no leg-failure path; filters must be applied inside both legs; the FTS pre-limit (`ORDER BY chunk_id DESC LIMIT 10000`) must come after filter joins, else a restrictive filter starves it. Its top-10 overlap with the full ranking was only 0.15-0.24 on synthetic text, so A-QUAL-2 on real text is a real gate (ADR-0001 amendment).

## 4. Paging and ordering
- Relevance: a score cursor is not reproducible (ANN is approximate, new files shift the pre-limit pool, RRF ties are common). Proposal: build the top-1 000 file-id list on page 1, keep ids only (no text) server-side for a short TTL, and page by position with an HMAC-signed opaque cursor bound to the user; page 1 always rebuilds so permission changes show at once. Storage (UNLOGGED table vs cache) is a design decision; Redis availability UNVERIFIED.
- Date and name orders: true keyset on `(mtime, file_id)` and `(name_key, file_id)` with row-value comparison and one direction for both columns; name order needs a fixed collation or a stored normalised key. Decision needed: apply the 1 000 cap after the sort key or among relevance candidates. A-FUNC-2 lists four orders while the architecture lists five (`name_desc`).
- Permission changes between pages can create short pages and gaps from dropped rows but not duplicates; the property test must define "no gap" as "nothing readable throughout is skipped".

## 5. Acronym expansion (the user's 1 000-entry glossary)
- PostgreSQL thesaurus dictionaries need files in the server's `tsearch_data` directory (not settable from SQL), apply at index time, and any change forces reindexing every `tsv` (3M chunks: GIN alone 182 s, WAL 13.6 GB in S0). Interaction with `unaccent` and the Spanish stemmer is undocumented: test before relying on it. Managed or unprivileged databases may not allow it (UNVERIFIED).
- Query-time expansion in PHP (build `tsquery` as `rem | (resumen <-> estadistico <-> mensual)`) needs no reindex, no DB-host access and is easy to highlight, but only covers acronym-in-query to long-form-in-text unless both directions are emitted. Recommendation for the design: query-time, both directions, the glossary versioned in the app; keep the thesaurus as a later migration. Ambiguous keys (SS, FA, PCR, CD, HD, EA, CCR, OT, IRA, ...) need a rule.

## 6. Filters
- File type: `file_meta.mime` exists (needs a mime-group map). Date: `file_meta.mtime` is bigint epoch. Folder subtree: **no data today**; the architecture says paths are computed per user and not stored. Options: stored ancestor-id array with GIN (ids only, no names), or resolve the folder to file ids through Nextcloud at query time. Owner and low-confidence filters (architecture) are outside the three chosen for R1.
- In the vector leg every filter is a post-filter inside the ANN CTE, so it compounds the ACL selectivity; the exact-scan switch should be computed after filters.

## 7. Eval harness
- No `make eval-search` exists. The S0 gold set (200 queries, `spikes/s0-harness/corpus/out/functional/gold.json`) has exact-lexical ground truth only; it cannot show a semantic or hybrid gain. A-QUAL-4 needs a gold set with paraphrase/acronym-relevant judgments over Spanish text, and a real embedding model. `bench/lib_load.py`, `m7_hybrid.py`, `m8_recall.py`, `prep_recall_corpus.py` are reusable but hard-coded to the throwaway `bd_spike` schemas.

## Decisions the design must take
1. Which Ollama model for the first profile (bge-m3 is the safest default on context and prefixes; cost: 1024-d), and how the profile records digest/prefixes/dimension.
2. Where Ollama runs for tests and for the S4 measurements (stub for CI; real model measurement needs a host and an owner, because the VPS Ollama is another project's).
3. Worker egress for ingest embedding; `allow_local_address` approach for query embedding; endpoint auth settings.
4. Vec lane: schema 3, vec-lane SECURITY DEFINER functions, own failure handling instead of the text-lane give-up, vector invalidation inside `write_result`.
5. RRF shape (leg depth, grouping), exact-scan threshold (1 000 vs 2 000 accessible chunks), relevance snapshot storage and TTL, cap placement for sorted orders, name collation.
6. Glossary: query-time expansion, ambiguity rule, both directions.
7. Folder-filter data model.
8. A real-text gold set for A-QUAL-2..4 and who judges it.
