# S3 research: events, reconciliation, scope and erasure

Environment note: read-only. Nothing was run against the `bd-s1` stack; Nextcloud was read from the image, groupfolders from the tarball. No network, so no URL citations; everything cites a file.

Citation prefixes:
- `repo:` = /root/buscador-documental
- `NC:` = `/usr/src/nextcloud` inside the pinned image (NC 34.0.4, `version.php`). The docker entrypoint copies it to `/var/www/html` at first start, so `/var/www/html/lib/...` does not exist in a bare `docker run`.
- `GF:` = groupfolders 22.0.6 (`lib/...`).
- **UNVERIFIED** = inferred or not runnable here. **INFERENCE** = follows from cited code but was not executed.

## 0. Six key findings

1. **File events: use the cache events, and treat every event as a hint to re-evaluate, not as the truth.** `CacheEntryInsertedEvent`, `CacheEntryUpdatedEvent`, `CacheEntryRemovedEvent` and the bulk `CacheEntriesRemovedEvent` (new in 34.0.0) fire for DAV, Node API and scanner changes. They are not complete:
   - a folder move fires one `CacheEntryUpdatedEvent` for the root only; its children are rewritten by bulk SQL with no events (`NC:lib/private/Files/Cache/Cache.php:800-882`);
   - user deletion removes the whole home storage with `Cache::clear()`, no per-file events (`Cache.php:901-911`, `NC:lib/private/Authentication/Listeners/UserDeletedFilesCleanupListener.php:64-68`);
   - deleting a system tag bulk-deletes its assignments and fires no per-object event (`NC:lib/private/SystemTag/SystemTagManager.php:327-344`);
   - share update (permissions, expiry, download attribute) has no typed event, only legacy `OC_Hook` (`NC:lib/private/Share20/Manager.php:682-815`);
   - groupfolders emits no typed ACL or applicable-group event, only string-typed `CriticalActionPerformedEvent` (`GF:lib/Folder/FolderManager.php:947,970,996`, `GF:lib/ACL/RuleManager.php:382,413,439`).

   So S3 should be level-triggered: the processor re-reads `oc_filecache`, tags and shares and decides, so ordering and lost events do not matter. The nightly reconciliation then covers exactly the gaps listed in section 1.

2. **The schema the architecture promises is not in the code.** `001_schema.sql` has no `outbox`, `tombstone`, `audit_log`, scope-rule or reconcile-cursor table. Verified with `grep` over `app/lib/Migration/sql`. `acl_dirty` is a bare boolean with no timestamp and no index (`001_schema.sql:27`), so the promised "backlog age in `occ status`" cannot be computed. `file_meta` has no storage id, so a deleted user's files cannot be found once NC has deleted `oc_storages` and `oc_filecache`. S3 needs a `004_*.sql` expand migration (new `Version…` class and its own grants; the grant statement in `003_roles.sql:30-35` only covers tables that exist when it runs).

3. **Groupfolders on NC 34 are separate-storage by default; S1's detection looks wrong for them.** In 22.0.6 `createFolder` always sets `separate-storage = true` (`GF:lib/Folder/FolderManager.php:899-909`). Each folder then has its own storage rooted at `<datadir>/__groupfolders/<id>` with `files/`, `trash/`, `versions/` inside (`GF:lib/Mount/FolderStorageManager.php:140-150`), and `group_folders.storage_id` and `root_id` hold the identity (`FolderManager.php:913-918`). `FileFactsSource` only recognises the legacy shared-storage path `__groupfolders/<id>/…` (`repo:app/lib/Acl/FileFactsSource.php:175`) and its unit tests only use that shape (`repo:app/tests/unit/Acl/FileFactsSourceTest.php:65-72`). INFERENCE: files in new groupfolders get no `g:<gid>` principal and no advanced-ACL flag. The failure is a false negative at the prefilter, never a leak, but the "all team folders" rule and the RBAC matrix must key on `group_folders.storage_id`. The first design task is one live probe (`select folder_id, root_id, storage_id, options from oc_group_folders` joined to `oc_storages`).

4. **Scope: rules store `fileid`, the check is an ancestor chain, and PostgreSQL has no path-prefix index.** `oc_filecache.fileid` is the global primary key (`NC:core/Migrations/Version13000Date20170718121200.php:233`), so one folder rule is one bigint that is independent of owner, mount and user view. PG gets no `(storage, path)` index because it is only created `!== PLATFORM_POSTGRES` (`:244-246`), so `path LIKE 'files/Dir/%'` over `oc_filecache` would scan. Use the parent chain (already how `ExclusionChecker` works, `repo:app/lib/Acl/ExclusionChecker.php:96-120`) per file and a recursive CTE over the `fs_parent` index (`:240`) per subtree. Trash and versions leave scope for free: they sit outside the `files/` prefix (home: `files_trashbin/`, `files_versions/`; groupfolder: `trash/`, `versions/`).

5. **Jobs: durable state must live in Postgres, not in the job row.** `QueuedJob` is removed before it runs (`NC:lib/public/BackgroundJob/QueuedJob.php:24-31`), a crashed `TimedJob` stays reserved for 12 h (`NC:lib/private/BackgroundJob/JobList.php:178`), `TimedJob` has no wall-clock scheduling (interval since last run only, `TimedJob.php:81-90`), argument JSON is capped at 32 000 chars (`JobList.php:31`), and `Job::start` logs the argument JSON at debug level (`NC:lib/public/BackgroundJob/Job.php:47`). Jobs are kicks; the cursor, the outbox and the lock are tables. Never put paths, names or uids in a job argument.

6. **Log hygiene has four real sinks beyond the app's own logger, and one is in S1/S2 code today.**
   - Apache access log: `%r` (request line with query string) goes to stdout (`/etc/apache2/apache2.conf:212-214`, `/var/log/apache2/access.log -> /dev/stdout`). A GET search would put query text in `docker logs`. `routes.php` has no search route yet, so S4/S6 must decide POST versus accepted residual.
   - Worker: `repo:worker/main.py:135` logs parser `detail` (up to 300 chars of parser-produced text), `:131` logs `BadAnswer`, `:178` `log.exception` prints the exception message and traceback, `repo:worker/parserd.py:22` prints `{e}`.
   - PostgreSQL `DETAIL: Failing row contains (...)` on a constraint violation echoes row values (page and chunk text), and the PHP exception message carries it into `nextcloud.log` (UNVERIFIED: documented PG behaviour, not run here).
   - Job arguments (above).

   The canary needs positive controls so the grep cannot pass vacuously (section 6).

### 1.1 Listener cost
`CacheEntryInsertedEvent`/`UpdatedEvent` fire for every `oc_filecache` row of every storage (previews, appdata, trash, versions); `admin_audit` already listens to the insert/remove pair (`NC:apps/admin_audit/lib/AppInfo/Application.php:132-133`), so the pattern is accepted. The listener must do almost nothing on the request path:
1. skip by the event's `getStorageId()` against a per-request memo of in-scope storages, and by `getPath()` prefix (`files/`, or the groupfolder equivalent). `AbstractCacheEvent` carries `storage`, `path`, `fileId`, `storageId` (`NC:lib/public/Files/Cache/AbstractCacheEvent.php:19-60`).
2. one `INSERT … ON CONFLICT DO NOTHING` into `outbox` (partial unique index on `(file_id) WHERE processed_at IS NULL`), same database connection, no filesystem access, no tag lookups. The row only says "re-evaluate file X" (and "re-evaluate subtree X" for folder events).
3. catch and swallow listener exceptions (log class name only): a failing index must never break a user's upload. The nightly job repairs it.
`registerEventListener($event, $listener, $priority)` is the registration API (`NC:lib/public/AppFramework/Bootstrap/IRegistrationContext.php:123`); `Application::register` is currently empty (`repo:app/lib/AppInfo/Application.php:21-22`).

### 1.2 Groupfolder ACL and grant changes: fingerprint poll (recommended)
Because there is no typed event, a TimedJob (every few minutes) computes, per groupfolder, a hash over `group_folders` (acl flag, `storage_id`, `root_id`), `group_folders_groups` (group, permissions, circle) and `group_folders_acl` rows for that folder's fileids, compares with a stored fingerprint, and on change marks that folder's files `acl_dirty`. Cost: one aggregate query per folder; independent of file count. Alternative or addition: listen to `CriticalActionPerformedEvent` and use it only as a trigger for the same poll (so a changed message text cannot silently disable it). Tables used: `group_folders`, `group_folders_groups`, `group_folders_acl`, `group_folders_manage`, `group_folders_trash`, `group_folders_versions` (names counted over `GF:lib`).

## 2. Background jobs in NC 34

### 2.1 API
- `OCP\BackgroundJob\TimedJob`: `setInterval(int $seconds)` (`TimedJob.php:32`), `setTimeSensitivity(IJob::TIME_INSENSITIVE|TIME_SENSITIVE)` (`:66`); runs when `now - lastRun > interval` (`:81-90`). Constructor takes `ITimeFactory` and must call `parent::__construct($time)` (`Job.php:31-33`). `run($argument)` is abstract (`Job.php:132`).
- `OCP\BackgroundJob\QueuedJob`: run once and removed **before** running (`QueuedJob.php:24-31`); no retry on crash.
- `IJobList` (`NC:lib/public/BackgroundJob/IJobList.php`): `add($job, $arg)` (deduplicated on class + argument hash, `JobList.php:30-47`), `scheduleAfter($class, $timestamp, $arg)` (since 28), `has`, `remove`, `getJobs`, `hasReservedJob`. Argument JSON max 32 000 chars (`JobList.php:31`).
- Overlap: `Job` allows parallel runs by default (`Job.php:28`); `setAllowParallelRuns(false)` (`Job.php:117`) makes `JobList::getNext` skip a job while another of the same class is reserved (`JobList.php:202-221`). Add a PG advisory lock as well (`pg_try_advisory_lock`), because jobs may also be launched by `occ`.
- Reservation: a job whose worker dies stays reserved until `reserved_at <= now - 12 h` (`JobList.php:178`). Design every job to finish within a time budget (for example 50-60 s per run, then return) and resume from a Postgres cursor.
- Registration: `<background-jobs><job>FQCN</job></background-jobs>` in `info.xml` (`NC:apps/files_trashbin/appinfo/info.xml:34-36` is the pattern), applied by `AppManager.php:1133` and `Installer.php:559` at enable/install. `repo:app/appinfo/info.xml` has only `<commands>` today.
- `Job::start` logs `Starting job <class> (id, arguments: <json>)` at debug and logs the full exception on failure (`Job.php:47-61`).

### 2.2 Shape for S3
| Job | Type | Interval | Does |
|---|---|---|---|
| `DrainOutbox` | TimedJob, no parallel | 60 s | claims N outbox rows `FOR UPDATE SKIP LOCKED`, re-evaluates each file (`FileFactsSource` + scope + `ExclusionChecker`), calls `FileIndexer::enqueue` or `IndexEraser::erase`, marks rows processed; stops at the time budget. |
| `ExpandSubtree` | same loop, driven by an `outbox` row of kind `subtree` carrying the folder fileid and a keyset cursor in a table | | walks descendants through the recursive CTE in 1 000-5 000 id batches. |
| `RecomputeAcl` | TimedJob | 60 s | processes `acl_dirty` ahead of backfill: `PrincipalWriter::writeFacts` per file, bump `acl_ver`, clear the flag. For a share on a 100k-file folder, use a set-based recursive CTE rather than 100k calls to `FileFactsSource::load` (about depth+3 queries per file, `FileFactsSource.php:133-203`). |
| `GroupfolderFingerprint` | TimedJob | 5 min | section 1.2 |
| `Reconcile` | TimedJob, `TIME_INSENSITIVE`, interval 24 h, plus a local-time window check in `run()` (NC gives interval-since-last-run only) | nightly | section 3 |
| `PruneRetention` | TimedJob | daily | outbox processed rows > 7 d (architecture §2), audit rows > retention, tombstones past `purge_after`, trash grace expiry. |

For a 100k-file folder the unit of work is a batch, never a folder: one batch is one short transaction, and the cursor lives in the table, so a killed job loses at most one batch. A `QueuedJob` may be used only as a "wake now" kick after a large operation (rule change, tag on a big folder); it carries an integer id.

In production, run a dedicated `occ background-job:worker 'OCA\BuscadorDocumental\BackgroundJob\DrainOutbox' …` loop (`NC:core/Command/Background/JobWorker.php:41-75`: job-class arguments, `--once`, `--interval`, `--stop_after`) or rely on cron; the choice is an S5 runbook item.

## 3. Reconciliation design

### 3.1 Facts that shape it
- The index lives in the **same PostgreSQL database** as Nextcloud (`aps_search` schema; migration runs through `IDBConnection`, `repo:app/lib/Migration/Version000001Date20261016000000.php`), so the manifest diff is SQL, not a PHP set transfer. `FileFactsSource` already reads `oc_filecache` through the same connection.
- Keys: `oc_filecache.fileid` is a global PK; `etag` changes on file change and, for folders, whenever a descendant changes (`NC:lib/private/Files/Cache/Propagator.php:78-88`). Folder etags are an optimisation hint only (INFERENCE for external writes before a scan).
- Home paths look like `files/top/mid/scan.pdf` on storage `home::<uid>` (`repo:app/tests/canary/scenario.sh`, the `FID=` query).

### 3.2 Passes (all keyset by `fileid`, chunks of 2 000-5 000, cursor persisted)
1. **Eligible set.** Materialise once per run into an UNLOGGED table `reconcile_node(run_id, file_id)`: union of recursive-CTE subtrees from the folder-rule roots and groupfolder storages, minus subtrees under `rag-excluded` tagged nodes (`ISystemTagObjectMapper::getObjectIdsForTags($tagIds, 'files', $limit, $offset)` pages the tagged ids, `NC:lib/public/SystemTag/ISystemTagObjectMapper.php:63`), restricted to `path` starting with the live prefix. Building it once avoids re-running the CTE per keyset batch (re-running costs O(subtree) per batch, quadratic overall). It also makes the run resumable across jobs.
2. **Forward diff** (eligible but not indexed, or stale): `reconcile_node n LEFT JOIN file_state fs` and `JOIN oc_filecache`: missing `file_state`; `fs.etag IS DISTINCT FROM f.etag`; `file_meta.storage_id <> f.storage` (needs the new column); `fs.text_state='skipped'` with a retryable reason (optional). Output: outbox rows.
3. **Reverse diff** (indexed but no longer eligible): `file_state fs LEFT JOIN oc_filecache f` where `f.fileid IS NULL` (deleted, includes user-purge residue) or the node is not in `reconcile_node` (out of scope, excluded, trashed). Output: erase (or tombstone for the grace case).
4. **ACL drift**: files whose recomputed principals differ from `file_acl.principals`. Do it set-based per top-level share/folder, not per file. Cheaper variant for the nightly: only files under folders whose share/ACL fingerprint changed; a full recompute weekly.
5. **Housekeeping**: tombstones past `purge_after`, `rag-excluded` tag presence and uniqueness, the orphan jobs in `job` for skipped files (`002_functions.sql:38-39` already drops them at claim time).

### 3.3 Cost at 1M files (**UNVERIFIED, not measured**)
- Pass 1-3 are index-driven joins on bigint keys: the order of magnitude is tens of seconds to a few minutes per million rows warm, longer cold. No S0 measurement of `oc_filecache` at 1M exists; the S0 harness measured chunks, not filecache. Add an `EXPLAIN (ANALYZE, BUFFERS)` check on the seed in the design/plan step (FRD says real-document validation is S5/S7).
- The per-file path is what must be avoided in bulk: `FileFactsSource::load` is about `depth + 3` queries (one row fetch, one parent query per level `:149-153`, one shares query `:158`, plus groupfolder queries `:176-185`). 1M files is roughly 6-12M round trips, an hour or more. So the bulk path is set-based and the per-file path handles only the diff, which should be small.
- Memory: never hold the manifest in PHP. Chunk size 2 000-5 000 ids; one transaction per chunk.
- Backlog protection: cap the number of outbox rows a single reconcile may add per night (backfill belongs to S5 and is throttled there); the rest continues next night from the cursor.

### 3.4 Tombstones and cursor
- **Level-triggered processing makes tombstones mostly a ledger.** If the processor recomputes truth from `oc_filecache`, tags and rules on every event, a later event can never resurrect a deleted file, so "delete beats earlier events" holds without timestamps. `oc_filecache.fileid` is a PG sequence value and is not reused (INFERENCE from `Cache.php:324` using `getLastInsertId`), so a tombstone keyed on `file_id` cannot be confused with a new file.
- What a tombstone is still needed for: (a) files whose `oc_filecache` row is gone (permanent delete, user deletion `Cache::clear`), where there is nothing to re-read; (b) the 30-day grace (`purge_after`) if the trash grace is kept (question Q4); (c) a deleted-user purge record. The architecture shape `(file_id, reason, purge_after)` (`01-architecture.md:36`) lacks `created_at`; add it so a restore after a tombstone can be ordered.
- Cursor: table `reconcile_run(run_id, started_at, phase, cursor_file_id, rules_fp, counts jsonb, finished_at)`. A job run advances the cursor within its time budget; the next run resumes; a run older than 36 h is abandoned and restarted. Store counters (missing, stale, orphan, acl_drift) for `occ status` and A-OPS-3 "per-file status visible": per-file status is `file_state.text_state/skip_reason` plus the new `reconciled_at` (or only the run counters; Q9).

### 3.5 A-OPS-3 test (reconciliation test)
Create/modify/move/delete files and change shares and tags in the stack, then `TRUNCATE aps_search.outbox` (simulating lost events) before running `Reconcile` through `background-job:execute`. Assert: missing file indexed, edited file re-queued, moved-out folder erased, deleted file erased, share-drifted principals corrected, tag-deleted case re-evaluated. ## 4. Scope rules

### 4.1 Decisions from the FRD to implement
`scope_mode ∈ {opt_in, all_readable}` (IAppConfig), folder rules, one groupfolder rule, `rag-excluded` always wins, previewable and audited, `occ` and admin page. `all_readable` is selectable only after counsel and DPIA are recorded (ADR-0006); same code path.

### 4.2 Storage
- **`scope_rule`** table: `id`, `kind ('folder'|'groupfolders')`, `file_id bigint NULL` (folder rule target), `created_at`, `created_by` (pseudonymisable), `enabled`. The groupfolder rule is one row (or one IAppConfig boolean), resolved at evaluation time to the set of `group_folders.storage_id`, so future team folders are covered with no rule edit (`GF:lib/Folder/FolderManager.php:913-918` stores `storage_id` at creation). Keep `scope_mode` in IAppConfig and the rules in a table so reconciliation can join them.
- Folder rule key is the **fileid of the folder**: stable across rename and move of the folder itself, independent of mounts and of which user views it. `occ buscador:scope:add --user <uid> --path /Folder` resolves with `IRootFolder->getUserFolder($uid)->get($path)->getId()`; the admin page does the same for folders the admin can see (Q6 for folders the admin cannot see).

### 4.3 "Is this file under an included folder?"
Per file (event path), reusing the existing walk:
1. Row: `storage`, `path`, `parent` (one query, as `FileFactsSource.php:134-141`).
2. Live-area guard: `path` begins `files/` (home storage and separate-storage groupfolder). Legacy root-jail groupfolders use `__groupfolders/<id>/files/…` (UNVERIFIED shape for the jail type; `FolderStorageManager.php:203+`). Trash (`files_trashbin/`, `trash/`), versions and appdata fail the guard.
3. Groupfolder rule: `storage ∈ group_folders.storage_id`, or the legacy path pattern.
4. Folder rules: ancestor chain via `parent` (cap 64, as `ExclusionChecker::MAX_DEPTH`, `ExclusionChecker.php:20`) intersected with rule fileids, with a per-call memo (as `ExclusionChecker::excludedAmong`, `:61-62`).
5. Exclusion: `ExclusionChecker` as today; exclusion beats scope.
Per subtree (rule change, folder move): recursive CTE `WITH RECURSIVE sub AS (SELECT fileid … WHERE fileid = :root UNION ALL SELECT c.fileid FROM oc_filecache c JOIN sub s ON c.parent = s.fileid)`, which uses `fs_parent` (`Version13000Date20170718121200.php:240`). Do not use `path LIKE` on PG (no prefix index, see finding 4). Add the preview as `count(*), sum(size)` over the same CTE joined to the supported mimetypes.

### 4.4 Moves in and out of an included subtree
- Same-storage folder move: one cache event for the root. Its handler enqueues a `subtree` task; the expander re-evaluates the root once and each nested rule or tag root, because scope is uniform below a root except at nested roots. Moving **out**: bulk erase of the subtree (`erase_file` is one transaction per file, `002_functions.sql:157-173`; a bulk `erase_files(bigint[])` SQL function with the same lock order is needed for 100k folders). Moving **in**: bulk enqueue behind the existing job cap.
- Cross-storage move: remove then insert events for the root, same fileid, children's `storage` rewritten in bulk (`Cache.php:818-822`). Same handler.
- A file moved within the included subtree needs only a metadata refresh (`name`, `mtime`); the content hash and etag are unchanged.
- A moved file keeps its `file_id`; `principals` may change (new ancestors' shares): mark `acl_dirty`.

### 4.5 Shares, mounts and "whose storage defines scope"
**Scope is the physical location**: the file's `(storage, fileid, ancestor chain)`, never a user's view. A file shared to ten users, or mounted in several places, is one `fileid` and has one scope answer. Shares affect only principals. Consequences:
- A file in an included folder of A's home that A shares to B is indexed once; B finds it via `u:B` plus the live recheck.
- A file outside every rule stays unindexed even if shared into an included folder, because the rule's subtree is physical. An admin who includes a received-share folder is including the owner's folder; resolving it with `getById` returns the owner-storage node, so the rule is created on that fileid.
- Multi-mount (same fileid reachable twice): the recheck already accepts any readable node (`01-architecture.md:45`).
- Mount events are not a trigger (section 1). Mount changes do not alter scope; they alter who can read, which the recheck covers.
- Display: a path for the admin page is computed live for the admin; do not store a path for user-facing output (architecture §2, `file_meta` row). Storing `storage_id` (numeric) is not a path and is not shown to users.

### 4.6 Related needs
- Etag staleness (S1 review #9): after S3 events flow, `Retrieve` can compare `file_state.etag` with the live node and show title-only until reindexed; the outbox shortens the window.
- Skipped-files table (S2 left it to S3/S6): `skip_reason` today is free text set by `fail_job` (restricted to eight values, `002_functions.sql:137`) and by `erase_file(p_reason)` (unrestricted). S3 adds `excluded`, `out_of_scope`, `trashed`, `user_purged`; add a CHECK or an enum table, plus the Spanish labels (section 7).

## 5. Erasure and audit

### 5.1 `rag-excluded` (A-SEC-3)
- Triggers: `TagAssignedEvent` where `getObjectType() === 'files'` and the tag id is one of the tags named `rag-excluded` (all of them count, `ExclusionChecker.php:80-89`, S1 notes M5). For a folder, enqueue a `subtree` task. `TagUnassignedEvent` re-evaluates the subtree (re-index if in scope).
- Erase: `IndexEraser::erase()` calls `aps_search.erase_file` (page, chunk, file_acl, file_meta, job deleted, `file_state` kept as `skipped(reason)`, `002_functions.sql:157-173`). The class comment names the stub `STUB(S3-listener-rag-excluded)` (`IndexEraser.php:14`) and `Application::register` registers nothing.
- A-SEC-3 "deletion, not hiding": the test is a row-count query per table (`page`, `chunk`, `file_acl`, `file_meta`, `job`, and later `chunk_vec_<gen>`) after tag assignment through the real event path, not the `ctl erase` shortcut the S1 canary uses (S1 review, gate-relevant).
- Physical residue: deleted tuples remain in the heap and WAL until vacuum, and in backups. State this honestly in the A-SEC-3 evidence and the DPIA; tune autovacuum on `page`/`chunk` (`01-architecture.md:70`).
- S4 forward compatibility: `chunk_vec_<gen>` tables do not exist yet; `erase_file` must reach them. Either FK `ON DELETE CASCADE` from `chunk_vec` to `chunk` (cost on bulk loads) or an erase function that iterates `embedding_profile.gen`. Q8.

### 5.2 User deletion (A-SEC-1 "user deleted", A-SEC-6)
What NC does (`User.php:262-326`): `BeforeUserDeletedEvent`; backend delete; group removals (events); user prefs removed; `UserDeletedEvent`. The home-storage cleanup is a listener pair: it captures the home storage in the before-event and does `rmdir('')` + `cache->clear()` in the after-event (`UserDeletedFilesCleanupListener.php:44-68`), because the before-event "might get canceled". Shares owned by or shared with the user are deleted by direct SQL (`Manager.php:1471-1481`, `DefaultShareProvider.php:1224+`).

What to erase from the index:
| Data | Action |
|---|---|
| Files on the user's **home storage** | Erase fully (delete the `file_state` row too, not `skipped`): NC deletes the files and the shares of them, so no other user keeps access. |
| Files the user shared **to others** from the home | Same as above: they disappear for everyone. |
| Files in **groupfolders** the user created | Keep: NC keeps them (groupfolders only deletes the user's manage/ACL rows, `GF:lib/Folder/FolderManager.php:1128-1139`). Only scrub `u:<uid>` from principals. |
| Files shared **to** the user by others | Keep; scrub `u:<uid>` from `principals` (GIN lookup `principals @> ARRAY['u:uid']`), bump `acl_ver`. This also prevents a re-created user with the same uid from passing the prefilter on stale grants (the recheck still decides; S1 review #19). |
| Jobs, outbox, tombstones for those files | delete |
| `audit_log` rows with `actor = uid` | pseudonymise (5.3) |
| `scope_rule.created_by` | pseudonymise |

Mechanics:
1. **Before-event**: capture, do not erase (it can be vetoed). Record `storage_numeric_id` of the home storage (same call as the NC listener: `IMountProviderCollection::getHomeMountForUser($user)->getStorage()->getCache()->getNumericStorageId()`, `UserDeletedFilesCleanupListener.php:44-47`) plus the uid in a `purge_pending` record or in the outbox payload.
2. **After-event**: run the purge. By then `oc_filecache` rows and the `oc_storages` row for the home are gone (and the order against NC's own listener is not guaranteed), so selection must come from the index: `file_meta.storage_id = :n`. Hence the new `storage_id bigint` column on `file_meta` (set by `FileIndexer`).
3. **Backstop**: the reconcile reverse diff (3.2 pass 3) erases any `file_state` whose `oc_filecache` row is gone, so a missed after-event heals within a night.
4. Ownership transfer before deletion moves files across storages with the same fileids (`OwnershipTransferService.php:469`): the stored `storage_id` goes stale until reconcile compares it (3.2 pass 2). This is why the compare matters before a purge.

### 5.3 Audit log: shape, pseudonymisation, retention
- Table (not yet created): `audit_log(id bigserial, ts timestamptz default now(), actor text, action text CHECK in list, file_id bigint NULL, detail jsonb NULL?)`. Action vocabulary from `04-security-privacy.md:29`: `retry_ocr, exclude, pause, resume, reindex, scope_mode_change, profile_change, purge_user`; S3 adds `scope_rule_add/remove`, `notice_ack`, `purge_user`, `erase_excluded`. No query text, no content, no file name or path in `detail`.
- Pseudonymisation options:
  (a) static `usuario eliminado`: loses correlation.
  (b) HMAC of the uid with an app secret: stable, but the key sits in `oc_appconfig` in the same database (ADR/IAppConfig sensitive is encryption at rest only), and a low-entropy uid is reversible by anyone holding the key; a key kept next to the data adds no protection.
  (c) **recommended**: a random per-user token generated at purge time (`usuario-eliminado-<8 hex>`), applied with one `UPDATE audit_log SET actor = :token WHERE actor = :uid` and recorded nowhere else. Irreversible by construction; investigators can still group one deleted user's actions. The `purge_user` audit row carries the token, not the uid.
  The `occ buscador:purge-user <uid>` command prints counts only, never names.
- Retention: 90 days proposed (open question #7, counsel). `PruneRetention` deletes `audit_log` rows older than the configured days; setting is an IAppConfig key with default 90. Trash/old-version grace 30 days (open question #4) is separate: the grace governs index data of trashed files, if kept (Q4).
- Who can write: `audit_log`, `outbox`, `tombstone`, `scope_rule` are NC-only tables. The worker role has no privilege on any table (`003_roles.sql`; `WorkerPrivilegeTest.php:13-24` enumerates all `pg_tables` of the schema, so new tables are covered automatically provided the migration does not grant to `bd_worker`).

### 5.4 `occ buscador:purge-user`
For a **deleted** user (uid unknown to NC) the command is the manual backstop of 5.2: it needs the storage id, which only the index knows. Take `--storage-id <n>` (or find it through `purge_pending`), or accept a uid and match `principals`/pseudonym tables; Q7. For an **existing** user it cannot simply erase: the nightly reconcile would re-index their in-scope files; either refuse unless `--exclude` sets a durable per-user exclusion rule, or restrict the command to deleted users. Options `--dry-run` and `--force`, output counts only, one audit row.

## 9. Questions for the design step
1. **Event granularity.** Confirm level-triggered processing (outbox row = "re-evaluate X"), and the `outbox` columns: `id`, `file_id`, `kind ('file'|'subtree'|'acl'|'rule')`, `created_at`, `processed_at`, attempts; dedupe by a partial unique index.
2. **Primary file listener.** Cache events (broadest, noisy) versus Node events (rich, but miss scanner/external changes). Recommendation: cache events with a cheap in-listener filter. Confirm that a failing listener must never break the request.
3. **`rag-excluded` flavour.** Which tag does the admin create: invisible/non-assignable (admin-only) or public (users can opt a folder out)? Decides who can trigger erasure (A-SEC-3) and whether the user-visible exclusion is a documented feature (S1 notes M5).
4. **Trash grace.** Keep index data of trashed files for 30 days (hidden by scope, cheap restore) or erase on trash (A-SEC-3 spirit, re-OCR on restore)? Counsel/user item (open question #4). If kept, state it in the DPIA and the notice.
5. **First run.** Does acknowledging the notice gate indexing, or only inform? What does a fresh install index before an admin adds a rule (nothing, by `opt_in`)?
6. **Rule target for folders the admin cannot see** (other users' homes). `occ buscador:scope:add --user/--path` versus a picker limited to the admin's view plus groupfolders.
7. **`purge-user` semantics** for existing versus deleted users, and how a deleted user's storage id is found (the `purge_pending` record versus a `--storage-id` flag).
8. **S4 forward compatibility.** FK cascade from `chunk_vec_<gen>` versus a generation-aware erase function; decide now so S3 erase tests do not need rework.
9. **Per-file status.** Is `file_state` plus `skip_reason` enough for A-OPS-3, or is a `reconciled_at` column wanted? `occ buscador:status --file`.
10. **Fingerprint poll vs `CriticalActionPerformedEvent`** for groupfolder ACL/grant changes (1.2); polling interval (acceptable false-negative window).
11. **`acl_dirty` model.** Per-file flags (a share on a 100k folder updates 100k rows) versus a dirty-roots table expanded lazily. Backlog age definition for `occ status`.
